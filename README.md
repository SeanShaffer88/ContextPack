## TL;DR

ContextPack generates one compact, AI-ready brief for any code repo —
identity, license (read from the file, never assumed), stacks and pinned
versions, build/test/gate commands, CI, docs, and a tree summary — so a
fresh AI session or subagent can load a project in seconds instead of
re-inspecting it from scratch. Standalone Python 3.10+, standard
library only, zero dependencies.

## Why

Every new agent session re-learns the same basics: What stack is this?
What version is pinned? How is it built and gated? What license is it
under? Getting any of those wrong is expensive — a license was once
assumed from a sibling project and was wrong. ContextPack answers all
of them from the files in the checkout, in one skimmable brief
(typically under 60 lines, capped design target ~250).

## Usage

```console
python contextpack.py pack <repo-dir> [--out CONTEXT.md] [--json context.json] [--max-files 400]
```

- Without `--out`, the Markdown brief prints to stdout.
- `--json <file>` also writes the same facts as structured JSON.
- `--max-files` (default 400) caps the scan; truncation is reported in
  the brief rather than hidden.

## Example brief (excerpt, generated by running ContextPack on itself)

```markdown
# ContextPack Brief: contextpack

> Generated — verify before acting; license and versions read from files at unknown (not a git repo / no HEAD).

## Identity
- Directory: `contextpack`
- Branch: Unknown
- HEAD: unknown (not a git repo / no HEAD)

## License
- File: `LICENSE`
- First line: MIT License
- Identifier (from file text): **MIT**

## Stacks
- **Python** — project `contextpack` v0.1.0, 2 .py files, requires-python >=3.10; pyproject.toml: yes

## CI
- `ci.yml` — name: CI
```

A real-world run on WinDevKit reported: HEAD `882cf43` on branch
`main`, 0 dirty files, license MIT, a Rust skeleton manifest under
`templates/dll-skeleton/`, PowerShell `tools/gate.ps1` plus
`tools/gate.sh` gate files, AGENTS.md present, and largest file
`tools/publish.py`.

## Supported stacks

| Stack | Detected from | Reported |
|---|---|---|
| Rust | `Cargo.toml` | package, version, edition, dependency count, workspace members |
| Python | `pyproject.toml` (tomllib on 3.11+, fallback parser on 3.10), `setup.py`, `requirements.txt`, `*.py` | project name/version, requires-python, dependency counts |
| .NET | `*.csproj`, `*.sln` | TargetFramework(s), solutions |
| Node | `package.json` | name, version, script names |
| Flutter/Dart | `pubspec.yaml`, `*.dart` | package name, SDK constraint, Dart file count |
| PowerShell | `*.ps1` | script count and paths |

Also detected regardless of stack: git remote/branch/HEAD/dirty count,
`gate.sh`/`gate.ps1` files, Makefile targets, workflows under
`.github/workflows/` (with their `name:`), the README `## TL;DR`
section, AGENTS.md, top-level `docs/`, file counts by extension,
largest files, and `.editorconfig` / `rustfmt.toml` / `.gitattributes`
presence.

## Limitations

- **Inference is heuristic.** Build/test commands are suggestions
  inferred from the detected stack — verify them against the repo's
  own README/AGENTS.md before running anything.
- License identification is a text-signature guess over the license
  file; the brief always shows the file and its first line so a human
  (or agent) can confirm it. If no license file exists, the brief says
  Unknown — it never borrows one from another project.
- TOML/YAML parsing is intentionally shallow: on Python 3.10 a small
  fallback parser handles common manifest shapes, and `pubspec.yaml` /
  workflow `name:` values are read with simple patterns, not full
  parsers.
- The scan skips heavy directories (`.git`, `node_modules`, `target`,
  virtualenvs, caches) and caps the file count; very large repos
  should raise `--max-files` deliberately.

## Development

```console
python -m unittest discover -s tests -v

```
